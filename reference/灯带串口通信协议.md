# Screen Strip Sync — 灯带串口通信协议

<!-- markdownlint-disable MD060 -->

本文整理 **PC ↔ 灯带** 的 USB 串口 ASCII 协议，供第三方理解或借鉴思路做二次开发。

本仓库是一个非官方的小上位机（屏幕同步控灯），**不是**厂商官方软件，也与小米、米家、Signify、飞利浦等品牌无关联；相关商标归其权利人所有。

进程间 IPC、配置文件约定见同目录 [进程间IPC协议.md](./进程间IPC协议.md)。实现经验见 [项目注意事项与踩坑.md](./项目注意事项与踩坑.md)。

---

## 声明与适用范围

- 设备侧内容来自 **Device Monitoring Studio** 串口抓包 + 黑盒压力测试，**不是**厂商公开文档。
- 串口协议仅在固件 `2.1.8_0039`（`version` 查询结果）上测过并据此整理；**未在其它固件版本上验证**。
- 目标设备对外写作：**米家追光灯带 Pro（非官方）**。米家模型字符串抓包为 `philips.light.strip3`。请勿把第三方电商俗称当成正式产品名宣传。
- 其它品牌 / 型号灯带**不保证**协议相同；逻辑或许相近，他人可借鉴本文思路自行验证。
- 帧过长会导致固件死机（需断电重启）。自行实验务必遵守文中长度与间隔限制。

## 一、硬件与物理层

| 项目 | 说明 |
| --- | --- |
| 物理灯珠 | 作者 **2 m** 版本：约 **每 10 cm 一颗**，共 **20** 颗（`get_length` 返回 `2`）。其它长度版本见下文猜测 |
| 米家模型 | `philips.light.strip3`（向设备发 `model` 时的返回值） |
| 测试固件 | **仅** `2.1.8_0039`（其它版本未测） |
| 协议形态 | 纯 ASCII 文本；作者**未发现**更原始的二进制控灯流。单片机侧每条指令大约只有 **~128 字节**量级文本能力，因此分辨率（段数）天然受限 |

其它物理长度（非 2 m）**未实测**。作者猜测：即便灯带更长/更短，逻辑控灯也很可能仍按 **2 m / 20 灯珠**做长度映射，而不是按真实米数无限加长 `set_rgb_pc`（文本帧长撑不住）。

### 串口参数（抓包 / 可用配置）

| 参数 | 值 |
| --- | --- |
| 波特率 | `230400` |
| 数据位 / 停止位 / 校验 | `8N1` |
| 流控 | 无 |

厂商软件打开串口时还会配置 DTR 置位、RTS 清除，以及 Purge、超时等。作者按此配置实现；**Device Monitoring Studio 抓包里也看到厂商软件做了同类设置**。各项是否缺一不可，未做「逐项关掉」对照实验；能稳定工作即可。

### 通信模式

- 纯 **ASCII 文本**。
- 每条指令以 `\r\n`（`0x0D 0x0A`）结尾；设备响应同样以 `\r\n` 结尾。
- `set_rgb_pc` **无任何 RX 应答**；其它控制指令通常回 `ok` 和/或 `rep_*`。

## 二、串口参数与初始化

打开串口时的配置语义（抓包所见 + 本项目采用）：

```text
SET_BAUD_RATE      → 230400
CLR_RTS / SET_DTR
SET_LINE_CONTROL   → 8N1
SET_CHARS / SET_HANDFLOW（无软件流控）
PURGE              → 清空收发缓冲
SET_TIMEOUTS       → 无数据时可立即返回
SET_WAIT_MASK      → 等 RX 等事件（厂商软件侧）
```

本项目 helper 使用 Win32 `CreateFile` + `SetCommState` / `SetCommTimeouts` / `PurgeComm` 等打开串口。

## 三、握手与查询

### 3.1 握手三步（进入 PC 控灯）

厂商抓包常见顺序：

| 步骤 | TX | 典型 RX |
| --- | --- | --- |
| 1 | `set_pc_available 1\r\n` | `ok\r\n` |
| 2 | `set_usb_dim_time <N>\r\n` | `ok\r\n` |
| 3 | `set_pc_linkage 1\r\n` | `ok\r\n` 以及 `rep_power` / `rep_pc_linkage` 等 |

说明：

- 交换顺序**大致可用**（未做严格正交测试）；按上表发最稳妥。
- `set_usb_dim_time`：**推测**为固件内部帧间渐变相关延迟（数值越大越柔和、延迟越高）。
  - 厂商抓包常见 `20`。
  - 本项目发帧间隔约 **50 ms**，因此握手里使用 `45` 作为缓冲（见代码 `handshake`）。
- 步骤 3 的多条响应有时会被设备合并成一次读。
- 见到联动成功后即可开始发 `set_rgb_pc`。

### 3.2 查询指令（可选）

用于识别设备，**非强制**。厂商软件在会话里会发，本项目可不发。

| 指令 | 抓包示例返回 | 说明 |
| --- | --- | --- |
| `get_pc_linkage\r\n` | `0` / `1` | PC 联动状态 |
| `get_power\r\n` | `0` / `1` | 电源 |
| `get_length\r\n` | `2` | 长度（单位按返回理解，本机为 2） |
| `version\r\n` | `2.1.8_0039` | 固件版本 |
| `model\r\n` | `philips.light.strip3` | 型号 |

## 四、设备状态报告 `rep_*`

`set_power 1` 等操作后，设备可能推送多行 `rep_*`（抓包里曾见到一整包状态）。  
下面字段名来自抓包原文；**多数含义没有逐一验证**，对接时不必依赖释义，保留原文即可。

示例（摘自一次抓包）：

```text
rep_length 2\r\n
rep_available 0\r\n
rep_tv_power 0\r\n
rep_linkage 0\r\n
rep_power 0\r\n
rep_bright 100\r\n
rep_pc_available 1\r\n
rep_pc_linkage 0\r\n
rep_master_type 0\r\n
```

相对有把握、且控灯会用到的：

| 字段 | 说明 |
| --- | --- |
| `rep_power` | 电源相关状态（0/1） |
| `rep_pc_linkage` | PC 联动是否建立（0/1） |
| `rep_bright` | 设备侧亮度报告，抓包为**十进制**（如 `100`） |

注意：`rep_bright`（十进制）与 `set_rgb_pc` 里的 `{Brightness}`（**两位十六进制**）不是同一套写法。`63` hex ≈ 99%，`64` hex ≈ 100%——按抓包与体感，**这一对应关系较可信**。

## 五、渲染帧 `set_rgb_pc`

### 5.1 语法

固件**不支持**局部增量更新；每一帧必须下发整条灯带全量状态（已确认）。

```text
set_rgb_pc {FrameID} 00 {Brightness} {HEX1} {Step1} {HEX2} {Step2} ... \r\n
```

| 参数 | 格式 | 说明 |
| --- | --- | --- |
| `{FrameID}` | 4 位 hex | 抓包中自增；**用途未严格验证**（推测与防抖/序号有关）。本项目按自增实现。 |
| `00` | 固定 | 抓包中始终为 `00`，**含义不清楚** |
| `{Brightness}` | 2 位 hex | **全局亮度**；数值约等于十进制百分比（较可信） |
| `{HEXn}` | 6 位 hex | RGB；抓包为小写，大小写敏感性**未专门测试** |
| `{Stepn}` | 十进制 | 该颜色占几颗物理灯珠 |

### 5.2 Step 规则（作者 2 m 版本）

- 作者 2 m 灯带共 20 颗灯珠：正常组帧应使所有 `Step` **之和 = 20**（本项目 10×2）。
- 若之和不等于 20：实测表现为**忽略**；仍建议始终凑满 20。
- 其它长度版本未测；结合「每条约 ~128 字节文本、无二进制流」的限制，作者猜测逻辑上仍可能按 2 m / 20 做映射，而不是按物理米数加长指令。

### 5.3 无应答

`set_rgb_pc` **确认无 RX**。不要在发帧循环里等待 `ok`。

### 5.4 亮度参考（抓包中出现过的值）

| hex | 约等于 | 场景 |
| --- | --- | --- |
| `64` | 100% | 满亮度约定 |
| `63` | 99% | 厂商默认工作亮度；**本项目固定写** `63` |
| `61` | 97% | 高频帧 |
| `20` / `1f` | ~32% | 渐变 |
| `19` | 25% | 低亮度 |
| `01` | 1% | 暗场 / 过渡 |

### 5.5 厂商驱动：5 段 × Step=4

抓包对象为**雷蛇（Razer）相关驱动版本**下的控灯流量：固定 **5 段、每段 Step=4**（5×4=20），串长约 70 字节。例如：

```text
set_rgb_pc 0001 00 63 00a3fe 4 00a3fe 4 00a3fe 4 00a3fe 4 00a3fe 4\r\n
```

暗场示例：

```text
set_rgb_pc 0005 00 01 000000 4 000000 4 000000 4 000000 4 000000 4\r\n
```

### 5.6 本项目：10 段 × Step=2

死机上限大约在 **130 字节**。按指令长度估算，理论上大约能做到 **11 段多**；本项目选用 **10 段、每段 Step=2**（10×2=20），是主动留安全余量，不是「协议只允许 10 段」。串长约 110 字节；代码层再拒绝 ≥120 的帧。

```text
set_rgb_pc 010a 00 63 ff0000 2 00ff00 2 0000ff 2 ffff00 2 00ffff 2 ff00ff 2 ffffff 2 ff8800 2 8800ff 2 ff0088 2\r\n
```

## 六、帧长与帧间隔

### 6.1 帧长（黑盒结论）

| 层级 | 数值 | 说明 |
| --- | --- | --- |
| 死机临界 | **约 130 字节** | 压测确认：到约 130 会死机；无可靠防溢出；需**断电重启** |
| 本项目拒绝线 | **≥ 120 字节不发送** | **安全策略**（留余量），不是「120 正好坏」 |
| 10 段方案 | 约 110 字节 | 相对约 130 死机线、约 11 段理论上限，主动留余量 |

不要为提高分辨率去逼近 130。真正 20 段（Step 全 1）会远超安全长度。

### 6.2 帧间隔

| 来源 | 间隔 | 说明 |
| --- | --- | --- |
| 厂商 / 雷蛇驱动抓包高频段 | 约 30–35 ms | 仅作对照 |
| **本机实测** | `WriteFile` **后 Sleep ≥ 50 ms** | **再短会丢帧**；50 ms 是作者测出的可用上限节奏（即最小安全间隔） |

本项目因此以 50 ms 为发帧节流，并把 `set_usb_dim_time` 设为 45 做缓冲。

## 七、电源与退出

### 7.1 `set_power`

```text
TX: set_power 0\r\n
```

- 灯会熄灭（变黑）。
- 是否总是附带清除 `rep_pc_linkage`：**未单独确认**。
- `set_power 0` **会清掉连接相关状态**；之后要重新控灯，需要再走握手（可先 `set_power 1` 再握手，视实现而定；本项目就绪路径里会 `power_on` + `handshake`）。

```text
TX: set_power 1\r\n
```

开电后设备可能推送状态行；细节不必当作稳定 API。

### 7.2 两种「关灯」：软关 vs 真下电

本项目把「看起来灯灭了」和「设备掉电 / 清联动状态」分开。

#### 软关灯（日常 UI「关灯」、休眠软关）

**不发** `set_power 0`。做法是：

1. 停掉追色发帧线程（不再抓屏、不再连发彩色帧）
2. 再发一帧全黑的 `set_rgb_pc`（10 段颜色全是 `000000`，Brightness 仍用 `63` 那套路；本项目走 `send_solid("000000")`）
3. 保持串口打开、PC 联动仍在

效果：灯看起来灭了，但设备仍处在 PC 可控状态。之后要再亮，直接发纯色 / `start` / `start_region` 即可，**不必重新握手**。

为什么要软关：进入 `set_pc_linkage` 之后，很多操作会被占住；若动不动就 `set_power 0`，状态会被清掉，下次还要 `power_on` + 握手，休眠唤醒、点一下 UI 关灯都会又慢又脆。软关只「画黑」，不拆连接。

#### 真下电（完全退出 helper、IPC `off` / `quit` 等）

要**真正熄灯并清掉连接相关状态**，发：

```text
set_power 0\r\n
```

- 灯会黑。
- **会清掉连接相关状态**；之后要再控灯，需要重新 `set_power 1`（如需要）+ 握手。
- 是否总是附带把 `rep_pc_linkage` 清成 0：**未单独确认**，以「状态被清、要重握手」为准即可。

作者退出建议：**直接 `set_power 0`**（不必先纠结 `set_pc_linkage 0`）。`linkage 0` 可作为可选释放步骤，但真下电以 `power 0` 为准。

### 7.3 和界面动作怎么对应

| 用户动作 | 走哪条 | 设备侧大致做什么 |
| --- | --- | --- |
| 界面「关灯」 | 软关 | 停引擎 + 黑帧 `set_rgb_pc`；**不下电** |
| 休眠软关（`sleep_sync` 开） | 软关 | 同上思路（黑帧，保留进程；细节见实现） |
| 托盘「退出」/ `quit` | 真下电 | `set_power 0` → 关串口 → helper 退出 |
| 备用命令 `off` | 真下电 | 停引擎 + `set_power 0`（界面很少用） |

IPC 命令名见 [进程间IPC协议.md](./进程间IPC协议.md)。

## 八、指令速查

### 写入

| 指令 | 格式 | 返回 | 用途 |
| --- | --- | --- | --- |
| `set_pc_available` | `set_pc_available {0/1}\r\n` | `ok` | 声明 PC 就绪 |
| `set_usb_dim_time` | `set_usb_dim_time {N}\r\n` | `ok` | 帧间渐变相关（推测） |
| `set_pc_linkage` | `set_pc_linkage {0/1}\r\n` | `ok` + 可能的 `rep_*` | 建立 / 释放 PC 联动 |
| `set_rgb_pc` | 见第五节 | **无** | 渲染帧 |
| `set_power` | `set_power {0/1}\r\n` | `ok` + 可能的状态 | 电源；`0` 用于真正熄灯并清状态 |

> 说明：真实串口指令里是空格加 `0` 或 `1`（例如 `set_power 0`）。上表用 `{0/1}` 表示二选一，避免 Markdown 表格把 `|` 当成列分隔符。

## 九、推荐会话流程

```text
打开串口 (230400 8N1，清空缓冲)
    │
    ▼ (可选) version / model / get_*
    │
    ▼ (本项目) set_power 1
    │
    ▼ 握手：available → dim_time → linkage
    │
    ▼ 循环：组 10 段帧 → 互斥写入 → Sleep(≥50)
    │
    ▼ 退出熄灯：set_power 0 → 关闭串口
```

在本仓库中，热路径全部在 `helper.exe` 内；界面只通过本机 IPC 发命令，不直接写串口。
