# Screen Strip Sync — 注意事项与常见坑

面向贡献者、移植者，以及想搞清楚「为什么这样设计」的第三方开发者。

协议细节见同目录：

- [`灯带串口通信协议.md`](./灯带串口通信协议.md) — PC ↔ 灯带
- [`进程间IPC协议.md`](./进程间IPC协议.md) — 界面 ↔ helper

---

## 1. 先搞清进程分工

本项目是双进程架构：

| 进程 | 角色 |
| --- | --- |
| `helper.exe` | 常驻后台：托盘、配置读写、串口、抓屏、组帧发帧、IPC 服务 |
| `screen_strip_sync.exe`（Flutter） | 可选界面：展示与改参、发命令；可随时关闭 |

正确预期：

```text
关闭界面 → 灯继续亮，helper 继续跑
托盘「退出」或 IPC quit → 关灯并退出 helper
```

如果做成「关掉 UI 灯就灭 / 后台也死」，就和当前产品语义相反了。

---

## 2. 架构为什么演变成现在这样

| 阶段 | 做法 | 问题 | 结果 |
| --- | --- | --- | --- |
| 早期 | Flutter 与 C++ DLL 同进程，经 `dart:ffi` 发帧 | 发帧线程和 UI 渲染抢资源，窗口一显示就容易丢帧 | 已放弃，目录中仍有历史代码 |
| 中间 | Flutter 当主进程，再拉起 helper | 开机自启不干净；关界面灯就灭；休眠/唤醒状态机很脆 | 已放弃 |
| 当前 | helper 常驻，Flutter 可有可无 | 解决上面三点 | 主线 |

结论：**抓屏 → 组帧 → 写串口** 必须离开 UI 进程；界面退出不应拖垮控灯服务。

仓库里带「废案」字样的目录仅供回顾，请不要当现行实现去改或去抄回主线。

## 3. 串口安全边界（最重要）

### 3.1 帧长：约 130 会死机，本项目在 120 处拒绝

- 黑盒压测：帧长到约 **130 字节** 会死机，只能断电重启（无可靠防溢出）。
- 本项目在代码里拒绝发送 **长度 ≥ 120** 的帧——这是**安全余量**，不是「120 正好坏」。
- 选用 **10 段、每段 Step=2**（10×2=20）：死机上限大约在 **130 字节**，按长度估算大约还能塞到 **11 段多**，这里留了安全余量，所以定 10 段，而不是去贴上限。本项目代码再在 **≥120** 处拒绝发送，又多留一层。
- IPC 行长上限是 512，和串口帧长无关。

### 3.2 帧间隔：至少 50 ms

- 雷蛇相关驱动抓包高频段约 30–35 ms 一帧（仅对照）。
- 作者实测：**再短就会丢帧**，因此 `WriteFile` 之后 **Sleep ≥ 50 ms**。
- 握手里 `set_usb_dim_time 45` 是配合约 50 ms 发帧节奏留的缓冲（厂商抓包常见是 20）。

### 3.3 互斥与停机顺序

- 所有写串口（含关灯、握手、校准高亮）应走同一把锁。
- 停止引擎建议顺序：**设停止标志 → 关灯 → `join` 线程 → 关串口**。顺序乱了，常见后果是 COM 被占住、关灯发不出去、下次打不开口。

### 3.4 渲染帧不要等回复

- `set_rgb_pc` 没有应答。在发帧循环里读串口等确认，很容易把线程堵死。

### 3.5 Step 之和与灯带长度（作者 2 m 版本）

- 作者手头是 **2 m** 灯带：约每 10 cm 一颗，共 **20** 颗；组帧时 Step 之和按 **20** 凑满（本项目 10×2）。之和不对时设备表现为**忽略**，仍建议模板写死，别依赖「忽略」。
- **其它物理长度**未实测。作者猜测：单片机侧每条指令大约只有 **~128 字节**量级的文本缓冲能力，协议只能走较「费字」的 ASCII，**未发现**更底层的原始二进制流；因此即便灯带更长/更短，逻辑长度也很可能仍按 **2 m / 20 灯珠**做映射，而不是按真实米数无限加长指令。
- 压测死机约在 **130** 字节；文档里的 128 / 130 都是同一量级的经验值（缓冲能力 vs 实测死机点），对外实现请以「远离上限 + 本仓库 ≥120 拒发」为准。

## 4. 亮度字段容易误判

### 设备事实

- `set_rgb_pc` 里的 `{Brightness}` 是**全局亮度**（hex 约等于百分比；`63` ≈ 99%，`01` ≈ 1%）。
- 观感明暗主要跟这个字段走。BRT 固定时只改 RGB 灰阶，灯上常常看起来像「只有全亮和全黑」。

### 本项目现状

- Brightness 目前**固定为 `63`**，这是已知取舍，不是疏忽漏接。
- 曾经考虑过的「按画面亮度驱动 BRT」方案已放弃。
- 「屏幕氛围」走的是另一条 region 采样路径，不是亮度模型。

### 排障提示

若感觉「平滑系数 α 没用 / 亮灭太硬」：

1. 先确认当前实现没有把 BRT 当可调通道；
2. 再查采样、超时、线程等问题。

请勿把「BRT 写死」直接当成要紧急修掉的回归 bug（除非你有意重新设计亮度通路）。

## 5. 进程与 IPC 易错点

### 5.1 单实例

| 进程 | 命名互斥体 |
| --- | --- |
| helper | `Local\ScreenStripSyncHelper` |
| Flutter | `Local\ScreenStripSyncUi` |

第二个 helper 实例不应再开串口、不应再监听 9527；通常只通知首实例打开界面后退出。

### 5.2 `bye` 和 `quit` 不同

| 命令 | 含义 |
| --- | --- |
| `bye` | 界面退出；helper **只关这条连接**，灯继续 |
| `quit` | **关闭后台服务**：关灯 → 停引擎 → 关串口 → helper 退出 |

把关窗做成 `quit`，会把「可关界面」做成「杀掉服务」。

### 5.3 互相拉起

界面兜底启动 helper 时建议：

1. 先连接 `127.0.0.1:9527`；
2. 失败再启动 helper，并带上 `--no-ui`；
3. 若不加 `--no-ui`，helper 可能再拉起界面，形成互相拉起。

### 5.4 托盘重复拉界面

建议三级判断：

1. 已有 IPC 客户端 → 推送 `ui show` 置顶；
2. 子进程仍在运行（含短暂冷却）→ 不再创建；
3. 否则再 `CreateProcess`。

否则连点托盘容易开出多个界面进程。

### 5.5 客户端断开不等于关灯

helper 不应因为 socket 断开就停引擎、关灯或退出。界面是可选的。

### 5.6 单客户端、仅回环

IPC 绑定本机回环，同时只服务一个客户端。不建议做成对外服务或多客户端同步。

## 6. 配置相关

- **写盘方只有 helper**。界面不应再直接写 `screen_strip_sync_config.json`。
- 帧长上限、50 ms 节流不要做成可配置项。
- 写盘建议 debounce（约 1 秒），不要放在发帧热路径里。
- 来自 IPC / JSON 的数值应在 helper 侧夹紧；非法整句可整句忽略。
- 缺字段、坏 JSON 应能回退默认并继续启动，而不是崩溃。

## 7. 抓屏与采样

### 7.1 Stride

DXGI / 位图行往往有对齐填充。若按「宽度 × 4」当行距，会把填充当像素读，出现亮度异常、画面亮闪。请使用真实的 `RowPitch` / stride。

### 7.2 DXGI 失效

分辨率变化、部分全屏独占、显卡重置等会导致 Desktop Duplication 失效。检测到后应重建，而不是继续读失效的映射。

### 7.3 两条路径不要混用参数

| 路径 | 入口 | 主要参数 |
| --- | --- | --- |
| map 屏幕跟色 | `start` | 段映射、α、near_black、blur、saturation |
| region 屏幕氛围 | `start_region` | bbox、algo、blur、smooth、dark |

段映射校准只服务 map；region 使用独立 bbox。  
`region_smooth` 与 map 的 `alpha` 语义极性相反：smooth 越大越「钝」。

### 7.4 截图框选在界面侧

框选与截图在 Flutter 完成；helper 只接收百分比矩形等结果。IPC 不传逐帧像素。

### 7.5 多显示器抓屏（2026年9月新增）

由于可能存在多块屏幕，DXGI 抓屏时需明确指定抓哪一块屏（`captureOutput`）。当拔插显示器时，Windows 内部的显示设备顺序或坐标可能会变动；代码里目前主要按显示设备名（DeviceName）或主显示器（Primary）进行稳定匹配，并在界面提供切换能力，避免拔插屏幕后 DXGI 默默地抓了错误的屏幕。界面上的选区百分比始终**相对于被抓取的那块屏**，而不是整个虚拟桌面。

## 8. 生命周期与电源

| 场景 | 预期行为 |
| --- | --- |
| 正常启动 | helper → 托盘 → 尝试开串口（失败也常驻）→ 监听 IPC → 拉起界面 |
| `--autostart` / `--no-ui` | 不拉界面；有串口则按上次场景恢复 |
| 打开界面 | 已有客户端则 `ui show`；否则创建界面进程 |
| 关窗 | `bye` 后界面进程退出；helper 不动 |
| 完全退出 | 关灯 → 停引擎 → 关串口 → 摘托盘 → helper 退出 |

休眠建议：挂起时软关（关灯 / 停引擎 / 关 COM），**进程保持**；唤醒后再按 `lastScene` 恢复。若用户关闭了休眠同步，则休眠期间不要插手。

息屏建议：通过注册显示器电源通知（Monitor Power Notification），在息屏时软关，亮屏后恢复。这与休眠同步是独立的两个配置项。

开机自启应注册 **helper**（带 `--autostart`），不要只注册 Flutter 界面。快捷方式同样应指向 helper。

开机瞬间 USB/CH340 可能尚未就绪，需要重试；串口暂时失败时，helper 仍宜留在托盘，方便用户稍后重连。

COM 打不开时，先查是否有残留 helper 或其它程序占用端口。当前版本对 COM 掉线的自动重连能力有限，主要依赖 `reconnect` 命令。

## 9. 路径与分发

- helper 查找界面：优先同目录 `screen_strip_sync.exe`，开发时再回退到 Flutter 的 `build\windows\...` 输出目录。
- 界面查找 helper：优先同目录，再回退到 `cpp_core\build\Release\helper.exe`。
- 请避免写死本机绝对路径。
- 对外分发时，helper 与 Flutter 运行时文件应放在同一目录；开始菜单 / 桌面快捷方式指向 **helper.exe**。
- `helper.log` 会在运行时自动轮转和限流（如抑制桌面静止时的 DXGI 无新帧报错），避免长驻后台时把硬盘写满。

## 10. 界面侧职责边界

| 适合做 | 不适合做 |
| --- | --- |
| UI、发 IPC、展示配置与状态、框选校准 | 写配置文件、直接开串口、EMA/组帧、常驻后台杀 helper |
| 在状态层（Notifier 等）里做副作用 | 在 `build` 里启动进程或开 Socket |
| 托盘菜单：根据实时运行时 intent 更新勾选状态 | 托盘菜单：根据 `lastScene` 更新状态（休眠或断开期间不同步） |

关窗建议语义：隐藏窗口 → 发送 `bye` → 退出界面进程。

状态管理请跟随仓库现有约定（Riverpod 的 `Notifier` / `NotifierProvider`）；新增代码时尽量不要再引入已淘汰的 API 风格。

## 11. 建议的排障顺序

遇到「灯不亮 / 丢帧 / 偶发卡死」时，建议按这个顺序查：

1. 帧长是否 ≥ 120 被拒绝，或是否逼近 130  
2. 帧间隔是否小于 50 ms  
3. 串口写是否绕过了互斥  
4. 停引擎顺序是否正确  
5. stride 是否算错  
6. 是否有 helper / 界面僵尸进程  
7. IPC 是否断开，helper 是否仍在  
8. COM 是否被占用  
9. 配置是否被多方乱写  
10. 最后再查采样算法本身  

若现象是「平滑无效 / 亮灭很硬」，请先看第 4 节的亮度说明。

## 14. 改动前自检清单

- [ ] 串口帧以 `\r\n` 结尾，长度 &lt; 120（远离约 130 死机线），Step 之和 = 20  
- [ ] `WriteFile` 后 Sleep ≥ 50  
- [ ] 写串口有互斥；停引擎顺序正确  
- [ ] 界面不直接碰 COM、不写 JSON、不杀 helper  
- [ ] 关窗使用 `bye`，完全退出才用 `quit`  
- [ ] 拉起 helper 时先试连，并带 `--no-ui`  
- [ ] IPC 仅本机回环、单客户端、不传像素  
- [ ] 讨论「α 无效」前先确认 BRT 是否固定为 `63`
